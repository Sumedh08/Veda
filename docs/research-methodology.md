# Research evidence and reporting rules

- Treat repository and paper inventories as leads. Preserve their label separately from what Veda itself retrieved or inspected.
- Represent source access as metadata-only, abstract-only, partial full text, full text, unavailable or error. Never imply that a search result or abstract represents a full paper.
- Keep exact evidence passages and stable source/document identity. A claim can be described as a source-reported statement without marking it independently verified.
- Appraise study design, population, geography, study period, intervention/exposure, comparator, measured outcome and measure, identification strategy, effect size/uncertainty, limitations, conflicts, missingness and external validity only where a stored source passage reports them. Missing values stay unknown; each non-unknown field retains same-source passage IDs and the model-assisted/unverified status.
- Distinguish association, causal estimate, forecast, theory, commentary and Veda-generated inference.
- Use support/refute/qualifies/insufficient labels with passage-level rationale. A contradiction requires explicit, passage-linked scope fields to agree; different outcomes, populations, geographies or periods can be heterogeneous. Missing scope yields incomparable rather than a contradiction. Comparison and competing hypotheses are model-assisted, not scientific verification.
- Check all citation IDs deterministically. Model-assisted semantic support checks are judgments, not scientific proof. Audit material uncited factual statements as well.
- Veda's semantic report audit is a separate structured model call from deterministic citation-link validation. Support verdicts are restricted to passage IDs already linked to the report item; invalid or missing assessments require review. The uncited-claim scan accepts only exact quoted substrings from its bounded report-text input, and reports whether that input was truncated. A model's empty scan result is not evidence that the report has no uncited material claims.
- Do not convert journal rank, citation count, publisher brand, writing style, company name or GitHub stars into truth scores.
- Reports disclose actual providers, queries, dates, access limits, source counts, failed steps, model judgments and estimated cost where available.

## Typed economic evidence and conditional implications

- Appraisal batch schema v2 keeps the existing source-method appraisal fields at schema v1 and adds claim-level `evidence_kind` plus separate population, intervention/exposure, comparator, outcome, estimate, uncertainty, geography, period, and measure facets. A model facet is stored only when its value links to the exact passage from which that claim was extracted; missing, duplicated, foreign, or unlinked facet values stay unknown or need review. These are model-assessed labels, not verified scientific facts.
- Official-statistics claims receive a separate deterministic transcription path. The stored indicator, observation value, geography, period, and measure are copied only when present in the exact generated observation passage. Their evidence kind is `descriptive_statistic`; uncertainty, population, intervention, comparator and study-effect fields stay unknown. A statistic is never relabeled as a causal study estimate.
- Report-draft schema v2 may return conditional decision implications only when the saved scope contains a `decision_objective`. Each accepted item carries an action, condition, rationale, assumptions, unknowns and claim IDs. Deterministic checks resolve those IDs and citations, reject explicit numeric tokens absent from the linked source-reported claims, reject `consider_pilot` without a linked study outcome and estimate, and reject `scale`, `pause`, or `avoid` unless a linked causal-estimate claim has passage-linked population, intervention, comparator, outcome, estimate and uncertainty facets. The gate narrows unsupported advice; it does not establish that the model's classification is correct.
- Accepted implications are included as separate items in the model-assisted semantic passage review and persisted in report verification metadata with their resolved claim, passage and citation IDs. UI inspection shows the assumptions, unknowns, provenance and source links. Semantic review remains advisory and does not replace a reader or domain expert.
- New reports use persisted report schema version 2. Older saved reports retain their original versions and remain readable.

## Provider-call budgets and replay

- Every structured provider operation is hashed over provider/model, schema, prompts and output-token limit. A completed operation replays only after its stored JSON validates against the same schema; changed prompts or schemas use a different cache key.
- Paid OpenAI calls atomically reserve a conservative per-job cost estimate and global/per-user daily call slots before dispatch. Recorded usage settles the estimate; an uncertain request keeps its reservation. Free OpenRouter routes reserve zero dollars and are rejected if the provider reports a nonzero charge, which is still recorded as observed usage.
- A process can fail after the provider accepts or completes a request but before Veda durably stores the response. The remote provider and Veda database do not share a transaction, so Veda cannot recover that response or know the exact charge. A stale reservation becomes `uncertain`; Veda retains its budget hold and does not automatically send the same operation again. This can leave an operation requiring operator reconciliation, but avoids silently duplicating spend.
- Concurrent workers that race after a cache miss are fenced by the unique operation/request-hash/attempt reservation. Only the winner dispatches; the other worker reads the durable state and replays a completed result or reports an in-progress/uncertain operation.
- These transaction and uniqueness checks have been exercised on local SQLite only. PostgreSQL semantics remain for T-09.

## Follow-up context boundary

- Each new job starts in a persistent project conversation. A follow-up must name a same-owner, same-project parent job and inherits that parent's conversation; malformed or cross-project links fail closed.
- Prior claim selection is a small, explainable lexical-overlap heuristic over at most the newest 100 passage-linked parent claims. At most eight positive-overlap claim IDs are retained. No match is a valid outcome; the code does not silently fill the context with unrelated recent claims.
- The history API resolves those IDs only against the parent job and returns the claim with its source title/access class and passage locator. This is a planning/inspection aid, not a verified relevance judgment.
- The parent question may frame follow-up queries and a dedicated planning subquestion. The child's extraction, appraisal, comparisons, deterministic citation map, semantic citation audit and report evidence set use only records retrieved for that child. Parent claims are not copied or cited into the child report.

## Decision-scoped plan (checkpoint schema version 4)

- A deterministic bounded planner creates the saved scope, analysis lenses, fixed query candidates, subquestions, stopping rules and resource caps. It records user-supplied decision objective/context, population, geography and time horizon; blank values remain explicitly missing rather than being inferred.
- If a provider is configured and the existing quota, budget, depth and replay gates allow the call, one structured model operation may choose an ordered subset of the fixed candidate indices and add at most two analytical questions. The model cannot author search-query strings, change explicit scope, remove direct-evidence/counterevidence requirements, change the methodological lenses or expand resource caps.
- Any disabled/unconfigured provider, exhausted limit, provider/schema failure, uncertain outcome, or invalid selection uses the deterministic plan. The saved v4 provenance and browser method label distinguish model selection from deterministic fallback and disclose a fallback reason. No live plan output is claimed unless the provider actually ran.
- Parent follow-up context may inform planning, but parent claims remain outside the child evidence set. The child's extraction, appraisal, comparisons, deterministic citation map, semantic citation audit and report use records retrieved for that child.
- The plan includes comparator/counterfactual, possible-outcome/denominator, confounder/selection/measurement and evidence-design lenses. They prompt later review; they are not provider filters and do not validate source relevance, answer quality, or causal interpretation.
- Plan schema v2 and v3 checkpoint records remain readable. The browser displays missing scope, each query and purpose, stop/abstention criteria, and the actual saved planning method/provider/model where available.
- The report records this boundary, and conversation history stores a short report-ready notice rather than treating model output as a persistent summary. User preferences are stored by authenticated identity. Project archive is restorable; archived projects can be permanently deleted after exact-title confirmation, and the owner can export Veda-managed records as JSON. Optional 30/90/365-day retention is recorded when archiving; expiration only executes when deployment maintenance is scheduled. Account deletion through the identity provider remains unsupported, and original HTML/PDF bytes are not stored or included in exports. Long-term semantic memory is not implemented.
