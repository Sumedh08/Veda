# Sarvam Token Factory: GLM-5.3 Flash compatibility review

**Checked:** 2026-10-31 against Sarvam's official public documentation.  
**Scope:** Exact model ID `glm5.3-flash`; no account or inference request was made for this review.

## Verified contract

- Sarvam lists `glm5.3-flash` as generally available on Token Factory. It is distinct from `glm5.3` and `sarvam-105b`. Its public model page lists a 1,048,576-token context window and both Chat Completion V2 (`POST /v2/chat/completions`) and Responses (`POST /v2/responses`) routes. The context figure is the combined prompt, reasoning and generated-output context, not a recommended output size. [Model page](https://docs.sarvam.ai/api/token-factory/models/glm-5-3-flash), [model catalog](https://docs.sarvam.ai/api/token-factory/models)
- Chat Completion V2 uses the `api-subscription-key` request header. The endpoint also accepts `Authorization: Bearer` for compatible tooling. The OpenAI-compatible SDK examples use the Sarvam key directly. [Chat Completions](https://docs.sarvam.ai/api/token-factory/chat-completions)
- GLM-5.3 Flash supports structured output. Chat accepts `response_format: {type: "json_schema", json_schema: {name, strict, schema}}`; Responses accepts the corresponding format under `text.format`. Sarvam says strict JSON Schema constrains shape, but applications must still parse and validate against their own schema and semantic rules. Veda should retain its independent Pydantic validation. [Model page](https://docs.sarvam.ai/api/token-factory/models/glm-5-3-flash), [structured-output documentation](https://docs.sarvam.ai/api/token-factory/chat-completions), [Responses API](https://docs.sarvam.ai/api/token-factory/responses-api)
- Chat V2 supports `reasoning_effort` values `low`, `high`, and `max`; omission defaults to `high`. GLM-5.3 Flash cannot disable reasoning. Responses accepts only explicit `reasoning.effort` values `low` or `high`; sending `max` returns HTTP 400, and omission defaults to `high`. Therefore use Chat V2 for Veda's current Sarvam adapter unless a concrete Responses API benefit justifies a separate adapter path. Set `low` explicitly for routine planning, extraction and appraisal; reserve `high` for a bounded comparison operation if the workflow establishes a need. Do not use `max` by default. [GLM-5.3 Flash parameters and reasoning](https://docs.sarvam.ai/api/token-factory/models/glm-5-3-flash), [Responses reasoning parameters](https://docs.sarvam.ai/api/token-factory/responses-api)
- Reasoning and final answer share the completion allowance. Chat uses `max_tokens`; Responses uses `max_output_tokens`. Sarvam advises explicitly setting these. The model page says requests above 1,048,576 output tokens fail with HTTP 400, but the context limit is shared with input and reasoning, so Veda must use much smaller workload-based caps and preserve its aggregate job budget. Reasoning tokens are billed as output tokens. [Model limits](https://docs.sarvam.ai/api/token-factory/models/glm-5-3-flash), [pricing](https://docs.sarvam.ai/api/getting-started/pricing)
- Chat responses report the exact returned `model`, `finish_reason`, `usage.prompt_tokens`, `usage.completion_tokens`, and `usage.total_tokens`. A `finish_reason` of `length` means the allowance ended; do not accept incomplete JSON. The model may include `message.reasoning_content` when reasoning effort is set, but the Chat response reference does not promise a separate numeric reasoning-token count for GLM-5.3 Flash. Do not derive token usage from the reasoning text. Preserve a separate reasoning count only if Sarvam actually supplies one. [Chat response fields](https://docs.sarvam.ai/api/token-factory/chat-completions)
- Known model errors include 400 for invalid parameters/context overflow, 403 for an invalid key, 404 for an unknown/unavailable model ID, 402 for exhausted prepaid credits, 429 for a request/concurrency limit, 503 for overload, and 413 for a request body over 10 MiB. A 402 is not retryable; model docs recommend backoff for 429/503, but Veda must retain its no-automatic-retry rule for uncertain inference POSTs. [Model error table](https://docs.sarvam.ai/api/token-factory/models/glm-5-3-flash), [pricing and rate-limit errors](https://docs.sarvam.ai/api/getting-started/pricing)

## Pricing and account controls

Sarvam's current public pricing table lists GLM-5.3 Flash at **₹13.50 per million input tokens**, **₹2.50 per million cached input tokens**, and **₹45 per million output tokens**. It states prices are in INR and exclude GST; reasoning tokens are billed as output. For conservative Veda reservations, use the uncached input price and full completion cap, plus the existing safety margin. Do not assume cache pricing. [Official pricing](https://docs.sarvam.ai/api/getting-started/pricing)

The billing documentation describes a prepaid balance at the organisation level, shared across products, workspaces and API keys. The dashboard exposes “Credits Left” under Settings → Billing and account-wide usage under Settings → Usage. The reviewed public docs do not describe a read-only API for retrieving the current balance or auto-recharge state. Account-specific remaining credit is therefore unknown to Veda unless the user verifies it in the dashboard. Auto-recharge can initiate a top-up when its threshold is crossed; the public documentation identifies it as a billing setting, not a request parameter. [Billing and payments](https://docs.sarvam.ai/api/platform/billing)

The public pricing page lists 50 requests/minute for a default-model set that names `glm5.3` but does not name `glm5.3-flash`. Do not assume that limit applies to Flash. The model page directs users to Dashboard → Rate Limits for current account/API-specific limits; exact account limits remain unknown without that dashboard. [Pricing and limits](https://docs.sarvam.ai/api/getting-started/pricing), [GLM-5.3 Flash model page](https://docs.sarvam.ai/api/token-factory/models/glm-5-3-flash)

## Implementation consequences for Veda

1. Register exact model ID `glm5.3-flash` separately from `glm5.3` and `sarvam-105b`; preserve `sarvam-105b` behavior.
2. Add a model-specific Sarvam capability profile: Chat V2 route, strict JSON Schema support, explicit `max_tokens`, `reasoning_effort` support `low|high|max`, reasoning cannot be disabled, and context window 1,048,576. Do not copy Sarvam-105B's plan-specific 4,096-token output ceiling into this model.
3. For a conservative initial profile, start with 8,192 or 16,384 completion-token ceilings only where fixture envelopes justify them, and lower task allocations as appropriate. These are application safeguards, not provider maxima. Keep total quick/standard/deep job budgets and per-request INR reservations independently enforced.
4. Send `reasoning_effort="low"` for routine structured calls and set the value explicitly for every call. Consider `high` only for evidence comparisons that need it. Account the entire `completion_tokens` field as billable output; record distinct reasoning usage as unknown when the provider does not return it.
5. Keep strict schema validation, exact source/passage ID validation, finish-reason checks, route identity checks, durable reservations, no-unsafe-retry, refusal classification and partial-evidence preservation unchanged.
6. Do not call the model available to Veda until the key-presence preflight, route configuration and cost reservation are valid. This note does not establish that the local credential is configured, that the account has ≥₹25 remaining, that auto-recharge is off, or that a real response conforms to Veda's schemas.
