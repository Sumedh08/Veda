# Restricted full-text retrieval decision

**Date:** 2026-10-29  
**Status:** Implemented locally behind document-license, exact reviewed-host, robots, and transport gates. The reviewed-host registry is intentionally empty, so full-text retrieval is denied until a host has been reviewed and recorded. No publisher or repository full text was downloaded during this review.

## Evidence and decision

OpenAlex defines `open_access.is_oa` broadly as the existence of readable full text, not as a reuse license. Its `best_oa_location` may be either a PDF or landing page, and each location's license can be unknown. OpenAlex also states that its downloaded PDFs retain their original copyright and that OpenAlex grants no additional rights. Veda requires `is_oa: true` plus an accepted `cc0` or `cc-by` location-license assertion. `public-domain` is not accepted because the identifier alone is not enough to distinguish a CC0 dedication from a public-domain mark or other rights statement. Unknown/restricted licenses remain metadata-only. HTML is attempted first and a location's PDF is the fallback under the same gates.

`best_oa_location` is selected because OpenAlex documents it as the best openly available copy; its `landing_page_url`, `pdf_url`, `license`, `version`, and host source are distinct metadata. The provider's license value is recorded as a provider assertion, never as independent legal verification. Retrieval also requires an exact, non-wildcard entry in `backend/app/research/retrieval-host-policies.json`, with a policy ID, reviewed terms URL/date, and allowed license identifiers. Entries older than 365 days, unknown hosts, and redirects to hosts without their own entry are denied. The checked-in registry is empty because this review did not establish terms for a particular live location. The application therefore continues with metadata and abstracts until a host-specific primary-source screen supports adding an entry. Veda persists the license source, policy record, robots result, final host, retrieval timestamp, media type, document SHA-256, access class, and exact HTML paragraph/sentence or PDF page/sentence locator. It stores bounded text passages, not raw HTML or PDF bytes.

Before requesting each HTML or PDF source URL, including each source redirect destination, the fetcher obtains and parses that origin's `robots.txt`. It uses the `VedaResearch` product token, supports user-agent groups, `Allow`, `Disallow`, `*`, `$`, longest-match precedence, and Allow on equal matches. Robots responses are bounded to 512 KiB, use at most five redirects, and are cached in-process for at most 24 hours. Veda uses a stricter policy than RFC 9309's optional 4xx access rule: non-200, malformed, oversized, or unreachable policy files deny retrieval. RFC 9309 states robots rules are not access authorization; a robots allow never substitutes for the independent license and reviewed-host gates. Robots redirect targets use the same SSRF-safe transport; source redirects require the destination host's own terms review.

For SSRF protection, a normal `resolve(host)` check followed by an independent HTTP-client DNS lookup leaves a rebinding window. Veda instead resolves the host, rejects the whole answer set if any address is not globally reachable, and connects directly to a checked IP while using the original hostname for the HTTPS `Host` header, TLS SNI, and certificate validation. Redirects are manual, limited to three, re-resolved and re-validated at every hop; HTTPS cannot downgrade to HTTP. User-supplied URLs are not accepted by this workflow. The fetcher ignores ambient proxy settings.

The Python standard library's `ipaddress.is_global` gives the public-routability test and documents mapped-address behavior; `http.client.HTTPResponse.read(amount)` permits bounded body reads. The HTML parser ignores script, style, iframe, SVG and template content. HTML responses are limited to 2,000,000 bytes, 8 seconds total, HTML/XHTML media types, identity content encoding, and at most 100,000 extracted characters. PDF responses are limited to 8,000,000 bytes, 8 seconds total, `application/pdf`, and identity content encoding. PDF parsing uses pypdf 6.21.4 or later in a short-lived subprocess with an 8-second hard timeout and no provider credentials; within a fetch this parser allowance is clipped to the remaining total retrieval deadline. Parser configuration caps streams, decoding work, xref entries, page-tree size, pages, per-page text (4,000 characters), and total extracted text (60,000 characters). It extracts embedded text only, does not OCR scans or inspect tables, and discards the original bytes after extracting a hash and passages. DNS work is capped at four concurrent lookups. Per-job caps are one/two/three attempted HTML pages, one/two/three PDF documents, and 12/36/72 stored full-text passages for quick/standard/deep.

## Why this transport differs from metadata clients

The scholarly APIs continue to use HTTPX with ordinary provider URLs. The source-document path uses the small direct-IP transport because it must keep the DNS address that passed the public-address check bound to the actual connection. This is custom networking code and carries its own maintenance risk; it is isolated in `backend/app/research/safe_fetch.py` and tested with injected resolver/socket fixtures. No live source website was fetched in tests. The fixture suite checks public-IP pinning, TLS hostname preservation, mixed/private DNS answers, redirects, downgrade rejection, license gating, response limits, MIME and active-content handling.

## Explicit limits

- This is local, fixture-tested behavior. It has not been validated against a live scholarly PDF, a particular publisher's terms, a production reverse proxy, or PostgreSQL. No host is currently enabled.
- Only `cc0` and `cc-by` OpenAlex identifiers are accepted, subject to the reviewed host record's license scope. An OpenAlex license field can be incorrect or stale and is not independent legal verification. Attribution and downstream model/report use still require review.
- The host registry is a manual evidence gate; it does not automatically interpret terms pages. Review the actual host, content source, and permitted use before adding an exact host record. The separate RFC robots gate is not a license or site-terms grant.
- The parser process has a hard wall-clock timeout and parser-level work caps, but no portable operating-system memory quota is installed. The PDF parser runs without network access or provider credentials; an OS-level memory sandbox is a hosting hardening item.
- Tables, images, scanned pages, OCR, attachments, forms, JavaScript actions, and embedded files are not extracted or executed. Text extraction does not itself establish scientific support.
- Research passages remain untrusted input. Appraisal and synthesis prompts label passages as evidence rather than instructions, and the model adapter exposes no tools; adversarial semantic prompt-injection quality still needs evaluation.
- Host-specific terms and license corroboration remain open under T-50; PostgreSQL migration/locking verification is tracked in T-09.

## 2026-11-02 addendum: separate private analysis from redistribution

The original CC-BY/CC0 plus exact-host registry described above is a conservative product policy, not a statement that copyright law always requires a Creative Commons license before private research access or analysis. It remains unchanged for its existing scholarly routes. A separate configured private-research path now applies to verified official HTML publications whose item license is not stated, subject to the requirements and limits in [ADR-0052](../architecture/ADR-0052-separate-private-research-processing-and-sharing.md).

The policy records distinct discovery, access, analysis, text retention, and sharing values. `RIGHTS_JURISDICTION` is blank by default; an unconfigured or unsupported jurisdiction remains metadata-only/review-required. The India profile is an operational statutory-exception candidate for a verified research work and private research use, not a legal opinion or universal authorization. It does not cover commercial or public-sharing use, software, explicit item/source restriction signals, direct document 401/403, or unresolved identity/terms. Where applied, at most four passages / 1,200 verbatim characters are retained, and sharing remains citation-only. The private workspace can inspect its evidence, while report and account-data exports withhold that source text and source-derived report text but retain bibliographic citation metadata.

The publication page metadata response is bounded and discarded after extracting identity metadata, item-level license declarations, a safe same-domain PDF link, and restriction signals; terms-page text is not retained, only its URL, hash and detected signal codes. This is a small automated screen, not a complete interpretation of every publisher's terms or document copyright statement. A signal or inaccessible terms page requires review. A missing terms page is recorded as `not_found`, not permission. No LLM makes the rights decision.

Robots-file outcomes are now distinguished per RFC 9309: a robots 4xx is recorded as “unavailable” and may permit the crawler to continue to an otherwise publicly accessible document; an explicit disallow blocks it; 5xx or network-unreachable rules fail closed. A direct document HTTP 401/403 remains an access denial. Robots status is not copyright permission or site-terms permission. No blocked source is retried through another fetch mode.

This is locally implemented and fixture-tested; no new unlicensed live document was acquired. The WIDER page whose robots endpoint returned 403 was not retried. See ADR-0052 and the current T-140 entry in `evaluation/RESULTS.md` for exact tests and remaining live validation.

Legal sources reviewed for the narrow policy statement:

- [Indian Copyright Act, Chapter XI, section 52](https://copyright.gov.in/Copyright_Act_1957/chapter_xi.html) includes specified fair-dealing purposes such as private or personal use including research; applicability to a particular source, access method, contract, amount, retention or downstream use is not resolved by this code.
- [IETF RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html) distinguishes robots 4xx unavailable from 5xx/network unreachable and states robots rules do not authorize copyright use.
