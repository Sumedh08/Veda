## Evidence that changes or narrows the initial assumptions

### Evidence and workflow

1. **Keep evidence-to-claim links as first-class data.** OpenScholar defines scientific synthesis around passage-grounded inline citations and reports ablations where removing reranking, iterative feedback, or citation verification reduced its measured correctness/citation performance. Its expert evaluation also found retrieval gaps and unsupported facts, and its benchmark's main domains do not cover business economics. This supports borrowing the *separate retrieval, attribution, and feedback gates*; it does not justify transplanting its corpus, training, or reported quality claims into Veda. `PAPER-INSPECTED (indexed text; direct page unavailable)`. [Nature paper](https://www.nature.com/articles/s41586-025-10072-4)

2. **Don't adopt PaperQA2 wholesale for the hosted MVP.** Its paper reports 248 LitQA2 questions, study-specific precision/accuracy and an “insufficient information” option; the authors also report a domain-specific contradiction benchmark. These are useful patterns, but the task is scientific literature and not SME ROI estimation. Current upstream code exposes an agent environment with a tool-driven search → evidence gather → answer path and settings for timeouts, concurrency, step limits, source counts and PDF parser choices. That is a valuable reference for bounded retrieval and abstention, but it brings a research-agent stack and optional PDF/embedding integrations that Veda would then have to adapt and operate. `PAPER-INSPECTED` for the arXiv text; `REPO-SOURCE-INSPECTED` for [`agents/main.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/agents/main.py), [`agents/env.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/agents/env.py), and [`settings.py`](https://github.com/Future-House/paper-qa/blob/main/src/paperqa/settings.py). [PaperQA2 paper](https://arxiv.org/abs/2409.13740)

3. **Citation auditing must inspect uncited statements too, and remains fallible.** DeepTRACE decomposes final responses into statements and measures source citation and factual support separately. The paper reports citation accuracy of 40–80% across tested systems; its LLM factual-support judge had Pearson correlation 0.62 with manual judgments on a 100-task sample. This is a warning against treating a generated bibliography or another model's green check as verification. Veda should first enforce deterministic source/passage/reference integrity, then label semantic checks as model-assisted and make uncertain claims reviewable. The paper evaluates the particular commercial systems and dataset it sampled; its rate is not a measured Veda failure rate. `PAPER-INSPECTED (full 22-page PDF)`. [DeepTRACE, ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/file/ad08767706825033b99122332293033d-Paper-Conference.pdf)

4. **Use generated “perspectives” to diversify search, not to assert camps.** STORM's peer-reviewed study reports improved article organization and breadth for its Wikipedia-like task, while editor feedback surfaced source-bias transfer and over-association of unrelated facts. Its code uses bounded conversations/search counts and serializes intermediate work to local output files. That is useful planning inspiration, but simulated personas are not evidence of actual economic schools of thought, and local files alone do not satisfy Veda's cross-device durability or Render's ephemeral filesystem. `PAPER-INSPECTED` for the ACL Anthology record/abstract; `REPO-SOURCE-INSPECTED` for [`storm_wiki/engine.py`](https://github.com/stanford-oval/storm/blob/main/knowledge_storm/storm_wiki/engine.py). [STORM paper](https://aclanthology.org/2024.naacl-long.347/)

5. **Commercial research adds intent clarification and evolving memory, but does not remove the need for Veda-specific evidence standards.** Mind2Report's 2026 arXiv record (which says the work was accepted to CIKM '26) describes intent probing, iterative search, citation-grounded memory and outline refinement; the paper reports results on its 200-query QRC-Eval. Treat all comparative scores as author-reported on that benchmark pending independent replication. Its current upstream repository README shows configurable LLM/search credentials and a local interactive run path; the source implementation and reproducibility were not audited in this pass. The original package points to a different GitHub owner than the arXiv record's current code link, so use the record-linked [USTC repository](https://github.com/ustc-ai4science/Mind2Report) as the candidate and verify its license, commit, code and dependencies before any reuse. `PAPER-INSPECTED` for the arXiv text; `REPO-DOC` for the current README. [Mind2Report paper](https://arxiv.org/abs/2601.04879)

6. **An end-to-end agent's citation prompt is not a validation gate.** In GPT Researcher's upstream `gpt_researcher/prompts.py`, the report prompt tells the model to cite every substantive claim and only use provided sources. That is a useful prompting convention, but it cannot itself enforce passage support or prevent unsupported uncited claims. The code was read via a mutable `main` URL; no behavior was executed. `REPO-SOURCE-INSPECTED`. [Prompt source](https://github.com/assafelovic/gpt-researcher/blob/main/gpt_researcher/prompts.py)

### Provider and hosting constraints

7. **The OpenAI integration should use the Responses API with strict structured outputs, while treating the schema as a format constraint rather than a truth constraint.** Current OpenAI docs describe Responses `text.format` with `type: "json_schema"` and `strict: true`; the API reference warns that only a subset of JSON Schema is supported. Structured output can still contain mistakes and refusals require explicit handling. The model ID should be configurable and checked against current model docs; do not hard-code a research workflow to a retired model. At the access date, OpenAI's pricing/model pages list GPT-6 Luna at $0.10 input / $0.50 output per 1M standard tokens and tool calls may incur separate charges. Any cost model must also count retries, long inputs, and tools; these public prices do not establish a per-job budget. `OFFICIAL-DOC`. [Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), [Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create), [models and pricing](https://developers.openai.com/api/docs/pricing)

8. **Render Free is suitable for previewing an app, but its Free Postgres is not the durable database the product requires.** Current Render docs state a Free web service has 512 MB RAM / 0.1 CPU, spins down after 15 minutes without inbound traffic and takes about a minute to wake; its filesystem is ephemeral and the service can restart at any time. Free Postgres is limited to 1 GB, has no backups or managed connection pooling, and expires after 30 days. Render also says Free instances are for testing/hobby/preview use, not production applications. Thus Render Free + Render Free Postgres does not meet Veda's promise of durable cross-device projects. Render Free can remain an optional demo host only if Veda uses a separate verified persistent database and the user accepts best-effort client-assisted job advancement; an alternative durable database's current free terms were not verified in this note. `OFFICIAL-DOC`. [Render Free services and limits](https://render.com/docs/free), [Render compute plans](https://render.com/docs/compute-plans)

## Provisional architecture decision

**Select A / E: a small custom, typed pipeline with database-backed stage checkpoints, hosted as a single API plus static web client. Reuse ideas from C, not whole research systems.** This is a provisional implementation choice, not a claim that it has been benchmarked against the alternatives.

- Keep the workflow explicit and bounded: plan; scholarly/official-source discovery; fetch and label access scope; store passages; extract claims/appraisals with passage IDs; compare only scope-compatible claims; perform deterministic citation checks; synthesize and audit; persist a report. Persist after each bounded step and let an active client request the next step. Use an external PostgreSQL database as the durable source of truth; never put durable state on a Render free filesystem.
- Adopt OpenAlex/Crossref/approved public sources through adapters as the no-paid-search baseline; make web search an optional provider with visible coverage and cost. Model output is validated against typed schemas and stored as `model_assessed`; stable source/passages/ownership and exact locators are validated by application code.
- Borrow PaperQA2's bounded retrieval/abstention ideas, OpenScholar's rerank-and-attribute lesson, STORM's query diversity, Mind2Report's intent-aware scoping and evidence notes, and DeepTRACE's uncited-claim and report-wide audit framing. Use a local-text/metadata retrieval baseline before paying for embeddings or adding heavy PDF infrastructure.
- Do not adopt GPT Researcher, PaperQA2, OpenScholar, STORM, or Mind2Report as the application core yet. Their tasks, dependencies, deployment assumptions, persistence, licensing, and evidence semantics differ; their benchmark results do not demonstrate fit for durable multi-user Veda. This is `INFERENCE` based on the evidence above, not a measured resource comparison.
- Do not add LangGraph for the first vertical slice. A plain finite-state workflow is sufficient until state transitions, branching, or retry logic become hard to audit; adopting a graph runtime is a migration option only if a prototype shows lower maintenance burden without hiding durable checkpoints, budget gates, or evidence provenance.

## OpenAlex Works API decision (2026-10-28)

The current OpenAlex API reference documents `GET /works`, `search`, `select`, a maximum page size of 100, and a Works response envelope with `meta` and `results`. The official search page says the Works `search` operation searches title, abstract, full text and keywords; it also reports a price of $1 per 1,000 search calls, while list/filter calls are $0.10 per 1,000. The authentication page documents a free keyless allowance, higher free-key budget, rate limits (10 requests/second without a key; 30 with a free key), and recommends exponential backoff after 429. OpenAlex states its data is CC0 and warns that text fields remain untrusted external content.

**Implementation choice:** use only the bounded Works `search` endpoint with selected fields and at most eight records per query; the provider streams at most 2 MB, times out, retries a 429 once, and sanitizes failures. OpenAlex account keys are not attached by default. The `OPENALEX_ALLOW_BILLABLE_CALLS=true` server setting is required before the optional configured key is sent in an Authorization header. No OpenAlex network call was made in this implementation task; fixture tests verify mapping, bounds, opt-in auth and failure handling. Crossref and OpenAlex records deduplicate by normalized DOI, and source metadata records the originating provider. T-41 now recomputes a Veda-local lexical score from the same original research question, title and bounded abstract excerpt; it ignores provider ranking, citation counts and venue prestige. Candidate feature records and exact order are persisted. This changes retrieval order only; T-38 must evaluate human relevance before any quality claim.

**Primary documentation accessed:** [OpenAlex API reference](https://help.openalex.org/api/), [Works search](https://help.openalex.org/api/searching/), [selecting fields](https://help.openalex.org/api/selecting-fields/), and [authentication/rate limits](https://help.openalex.org/api/authentication/). These pages describe current provider behavior, not research coverage or independent service availability.

### What this means for the provisional deployment choice

Neon changes the earlier open question: a free managed PostgreSQL service with no documented fixed expiration is available, so Veda can prepare for persistent hosted projects without relying on Render's expiring Free Postgres. A low-traffic MVP would still be constrained to 1 GB storage, 100 CU-hours and 5 GB egress per Neon project each month, with five-minute scale-to-zero behavior and community-only support. At 0.25 CU the compute allowance corresponds to at most 400 active compute hours per month before suspension; real usage varies with compute size and concurrency. After quota exhaustion, the data remains stored but users cannot access it through the suspended compute until reset or upgrade.

Supabase remains a credible integrated Postgres+Auth option if the project stays active and export/restore operations are owned by Veda. Its free-tier 7-day inactivity pause and 1-year restore window make it a weaker fit for unattended durability. Both providers put Auth state inside or directly alongside the Postgres service, simplifying identity-to-row references but coupling login availability to the database/provider. In either case, Veda must validate identity server-side and scope each project and nested resource to that identity; a vendor-managed Auth product is not an authorization test.

**Decision update:** use Neon as the first candidate for a non-production deployment spike, subject to no-cost account access, a FastAPI JWT-validation proof, migrations, fresh-user ownership checks, usage-limit handling, and a documented backup/export drill. Keep standard PostgreSQL migrations and a provider interface so moving to a paid/managed service does not require a data-model rewrite. Until a successful authenticated connection and restore/export test occurs, mark hosted persistence `NOT TESTED`; do not describe this free tier as production-durable.
